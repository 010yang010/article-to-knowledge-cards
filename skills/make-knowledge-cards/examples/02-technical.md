# 示例 2 · 技术类（概念 + 代价 + 常见误区）

## 原文

> 数据库索引是一种帮助数据库快速查找数据的结构，最常见的是 B+ 树索引。没有索引时，数据库只能做全表扫描，逐行比对，数据量越大越慢。有了索引，数据库可以像查字典目录一样，快速定位到目标数据的位置，把查找从 O(n) 降到接近 O(log n)。
>
> 索引不是免费的。它占用额外的存储空间，并且在插入、更新、删除数据时需要同步维护，会降低写入性能。因此通常只为频繁查询、区分度高的列建索引。
>
> 另一个常见误区是把所有列都加上索引。索引过多不仅浪费空间，还会拖慢写操作，甚至让查询优化器更难选择最优执行计划。合适的做法是针对高频查询条件建立少量有针对性的索引。

## 生成卡片（5 张）

### 卡片 1：索引是什么——数据的"字典目录"
- **核心知识**：数据库索引是一种加速查找的数据结构，最常见的是 B+ 树索引。
- **简明解释**：它像书的目录，让数据库不必逐页翻找就能直接跳到目标位置。
- **例子 / 自测问题**：没有目录时，你如何在一本 1000 页的书里找某个关键词？这与全表扫描有什么关系？

### 卡片 2：索引把查找从 O(n) 降到约 O(log n)
- **核心知识**：无索引时需全表扫描（O(n)），有索引后可快速定位（约 O(log n)）。
- **简明解释**：数据量越大，有无索引的差距越悬殊，这就是大表查询"加个索引就快了"的原因。
- **例子 / 自测问题**：当数据量从 1 万行涨到 1 亿行，全表扫描与索引查找的差距大约会扩大多少倍？

### 卡片 3：索引是有代价的——占空间且拖慢写入
- **核心知识**：索引会占用额外存储，并在增删改时增加维护开销，降低写入性能。
- **简明解释**：每多一个索引，写操作就要多更新一棵树，因此索引是"用写性能换读性能"。
- **例子 / 自测问题**：一个频繁写入、很少查询的日志表，是否应该建很多索引？为什么？

### 卡片 4：何时该建索引——频繁查询且区分度高的列
- **核心知识**：通常只为查询频繁、区分度高的列建立索引。
- **简明解释**：区分度低（如"性别"只有两三种值）的列建索引收益很小，优化器甚至可能不用它。
- **例子 / 自测问题**："用户状态"（仅 启用/禁用 两种）这样的低区分度列，是否适合单独建索引？

### 卡片 5：误区——索引不是越多越好
- **核心知识**：给所有列都加索引是常见误区；索引过多会浪费空间、拖慢写操作并干扰优化器。
- **简明解释**：恰当做法是针对高频查询条件建立少量、有针对性的索引，而非"全覆盖"。
- **例子 / 自测问题**：如果一个表有 20 个索引但每天只做几次查询，主要隐患是什么？
